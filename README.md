# HumorHist

A pipeline that turns historical oddities into LLM-assisted research and "comic
angle" briefs for a humorous-history social account. Fact-checking is not a
guarantee: a human should verify the claims and sources. A human still writes the actual
jokes — humorhist does the research and hands you angles, source links, and the
"watch out, the popular version is a myth" flags.

Use the CLI or the Telegram bot; optional `systemd --user` services and timers
run the bot and scheduled jobs. The stages are:

    harvest  ->  screen  ->  draft  ->  (you review)  ->  copy  ->  publish*

    * `publish` exports content for manual posting; it does not post remotely.

-------------------------------------------------------------------------------
## What it actually does
-------------------------------------------------------------------------------

- harvest  Gather candidate historical events into a pool (curated seed events +
           Wikipedia-list events out of the box). Title normalization helps
           collapse duplicates across sources; it is not exhaustive.
- screen   Ask an LLM to score each event 0-10 on how absurd/funny it is, so
           drafting can later pick the best ones.
- draft    For the top-scored events: fetch the Wikipedia article, run a
           fact-check pass (separating the documented record from the popular
           myth), then generate several distinct comic angles with setups,
           "why it lands", pitfalls, and raw material you can use.
- show     Print a single draft in full so you can read and judge the angles.
- status   Pool/draft health at a glance.
- copy     Approved drafts are queued. A first-draft post may be generated by
           the review workflow when an LLM is available; generation can fail or
           be skipped, so copy is not guaranteed. `copy show/edit/regen`
           let you read, rewrite, or regenerate that copy in place before any
           destination posting. (See "Phase 4: post copy" below.)

The output of `draft` is a structured brief: fact-check results, dates, key
figures, caveats, misconceptions, sources, and 3-5 comic angles. You read it
and write the post yourself.

-------------------------------------------------------------------------------
## Requirements
-------------------------------------------------------------------------------

- Python 3.11+
- The only runtime dependency is `httpx` (tests use `pytest` + `respx`).
- Wikimedia request coordination uses POSIX `flock`; all cooperating CLI,
  Telegram and scheduled processes must run as the same user with the same HOME.

Wikipedia requests share a persistent pacing/cooldown state under
`~/.cache/humorhist/`. A 429 or redirect `Retry-After` blocks all cooperating
processes until its full deadline; absent 429 hints use 60 seconds. HTTP 403
blocks indefinitely pending review, and its known Retry-After (or 60-second
fallback) is a minimum before reset. Malformed hints and process death during a
request also block indefinitely. Transport errors impose a 60-second cooldown,
but cannot establish whether an unseen server response specified a longer one;
investigate before retrying if a request may have reached Wikimedia.

The lock covers the entire HTTP request. HTTPX's 30-second timeout is an
inactivity timeout, **not a total deadline**: a slow peer could hold the lock
indefinitely. Other producers fail visibly after a 5-second lock wait. Identify
and stop the stuck producer rather than deleting the lock file. Different users,
homes, containers, and external clients do not share coordination. Stop all
producers before upgrading: older versions do not understand the current state
format, and mixed versions cannot safely share limiter state.

### Offline rate-state recovery

1. Stop all producers using this HOME (CLI, Telegram, timers, scheduled jobs,
   and any manual jobs), prevent scheduled restarts, and verify no producer or
   in-flight request remains. Inspect service/timer and process status; do not
   assume stopping one process stops all producers. Use the same user and HOME.
2. Run `python -m humorhist.wikipedia inspect`. It acquires the same lock and
   shows the reason and deadline without contacting Wikimedia. If the lock
   times out, a producer may still be running; investigate before proceeding.
3. Investigate the interrupted request, 403, or malformed response and review
   Wikimedia's access policy and any provider instructions. Obtain permission
   to resume where required. A malformed hint or lost response can conceal an
   unknown deadline: reset only after establishing it is safe and permitted.
4. Once all producers are stopped and permission reviewed, run
   `python -m humorhist.wikipedia reset --confirm-producers-stopped-and-permission-reviewed`.
   The command refuses to shorten a known unexpired deadline. It cannot verify
   your confirmation. Invalid/corrupt state is refused because its deadline is
   unknown; investigate and recover it manually only after establishing the
   provider's restriction has expired and permission to resume. Never remove
   or replace the lock file. Restart producers only when permitted.

## Configure the LLM
-------------------------------------------------------------------------------

Configure the LLM with environment variables; keep credentials out of the repo.
CLI commands using the default client require an API key. The Telegram bot and
scheduled jobs prefer the key and can fall back to the Nous OAuth token in
`~/.hermes/auth.json`; that token is temporary and is not a reliable unattended
credential. Use `python -m humorhist.cli llm-check` to inspect credential readiness.

    HUMORHIST_LLM_API_KEY     API key for a chat-completions API; recommended
                              for unattended jobs.
    HUMORHIST_LLM_BASE_URL    Optional. Default: https://inference-api.nousresearch.com/v1
    HUMORHIST_LLM_MODEL       Optional. Default: tencent/hy3:free
    HUMORHIST_CHAR_LIMIT      Optional. Max length of generated post copy
                              (default 280). Raise it (e.g. 280 -> 400) if you
                              later post to a platform with a larger limit.
    HUMORHIST_IMAGE_PROVIDER  Optional: fal (default for backward compatibility)
                              or openai. OpenAI is never selected implicitly.
    HUMORHIST_IMAGE_API_KEY   FAL key only; enables FAL story images when set.
    OPENAI_API_KEY            Separate OpenAI key, used only with provider=openai.
    HUMORHIST_IMAGE_STYLE     Optional. One of: editorial-historical (default),
                              editorial-cartoon, meme.
    HUMORHIST_IMAGE_DIR       Optional. Where generated PNGs are written
                              (default: <data dir>/images).
    HUMORHIST_IMAGE_MODEL     Optional. FAL model id (default: fal-ai/flux/dev),
                              or OpenAI gpt-image-2.5-flare (default),
                              gpt-image-2.5-sunburst, gpt-image-2, gpt-image-1.5.
    HUMORHIST_IMAGE_QUALITY   OpenAI only: low (default), medium, or high.

Image generation may incur provider charges, and image-prompt generation can
also use the configured LLM. OpenAI sends one 1024x1024 PNG request per image.
Both providers make no automatic retries of a paid submission, including on
timeouts: a failed response may still have incurred a charge. Check your
provider dashboard before manually retrying. Set provider budgets/spending limits.
OpenAI lists `gpt-image-1.5` and `gpt-image-2` as deprecated; check its
[deprecations page](https://developers.openai.com/api/docs/deprecations) before
using those legacy choices.
Approval, enqueue and queue backfill never generate images automatically.
Generate one explicitly with `python -m humorhist.cli image <draft_id>` or
Telegram `/image <draft_id>`; repeating either command requests another paid
image, including when the previous request may have timed out.

For example, to opt into OpenAI explicitly (set the key securely in your
environment, never in the repository):

    export HUMORHIST_IMAGE_PROVIDER=openai
    export HUMORHIST_IMAGE_MODEL=gpt-image-2.5-flare
    export HUMORHIST_IMAGE_QUALITY=low

The client speaks the OpenAI-compatible /chat/completions schema, so any
provider that exposes that endpoint works — point BASE_URL at it and set the
key. Example:

    export HUMORHIST_LLM_API_KEY="your-key-here"
    export HUMORHIST_LLM_MODEL="tencent/hy3:free"

## The database
-------------------------------------------------------------------------------

The main data lives in a SQLite file. The CLI default location is:

    ~/projects/humorhist/data/humorhist.sqlite

Override the default with `HUMORHIST_DB` or per command with
`--db /path/to/db.sqlite`. Generated images and runtime logs are separate files;
the SQLite file, images and logs are git-ignored.

Main tables:
- pool   — candidate events (title, year, summary, funny_score, status).
- drafts — generated briefs (brief_json, angles_json, status).
- queue  — approved items, post copy, source/image metadata and manual-post state.
Telegram also uses a per-draft version table to reject stale actions.

-------------------------------------------------------------------------------
## Usage
-------------------------------------------------------------------------------

All commands accept `--db` to point at a specific database.

### 1. Harvest the candidate pool

    python -m humorhist.cli --db data/humorhist.sqlite harvest

Options:
    --seed-only          only load the curated data/seed_events.csv
    --wikipedia-only     only pull from the configured Wikipedia list pages

Idempotent: re-running never duplicates rows or overwrites existing scores.

### 2. Screen (score funniness)

    python -m humorhist.cli --db data/humorhist.sqlite screen

Options:
    --batch-size N       events per LLM call (default 20)
    --limit N            only score the first N unscored events

Only rows with a NULL score are scored, so re-running is safe.

### 3. Draft (fact-check + angles)

    python -m humorhist.cli --db data/humorhist.sqlite draft

Options:
    --count N            how many candidates to draft (default 3)
    --min-score F        only consider events scored >= F (default 7.0)

Candidates are sampled from a window 4x larger than --count so repeated runs
don't always pick the same few. Each draft is written with status "pending"
and the source pool row is marked "drafted".

### 4. Review a draft

    python -m humorhist.cli --db data/humorhist.sqlite show          # most recent
    python -m humorhist.cli --db data/humorhist.sqlite show <id>     # specific draft

Prints the verified facts, misconceptions (popular myth vs record), caveats,
sources, and every comic angle. This is the part you read before writing a post.

You can review interactively from the terminal:

    python -m humorhist.cli --db data/humorhist.sqlite review

It walks pending drafts ready for review, shows them, and prompts `[a/r/s/l]`
(approve/reject/skip/later) plus optional editor line + notes.

### 4b. Review from Telegram (optional)

Instead of the terminal, run a Telegram review loop and approve/reject from
your phone with inline buttons, and see at a glance which topics you've already
decided on.

**One-time setup**

1. Create a bot via @BotFather and copy the token it gives you.
2. Find its username (also from @BotFather) and **open that bot in Telegram /
   send it any message** — this registers your chat so the bot can DM you.
3. Get your private numeric chat id. After messaging the bot, run the following;
   enter the bot token at the hidden prompt, not in a command or shell history:

       python3 - <<'PY'
       import getpass
       import json
       from urllib.request import urlopen

       token = getpass.getpass('Telegram bot token: ')
       try:
           with urlopen('https://api.telegram.org/bot' + token + '/getUpdates', timeout=15) as response:
               updates = json.load(response).get('result', [])
       except Exception:
           raise SystemExit('Telegram request failed; check the token and connection') from None
       chats = [u['message']['chat'] for u in updates if 'message' in u]
       private = [c['id'] for c in chats if c.get('type') == 'private']
       print(private[0] if private else 'Message the bot privately first')
       PY

   Only one process may poll `getUpdates` at a time. Stop the review loop before
   running this, then restart it afterward. Never share the token.
4. Put the token and chat id in a local `.env` (gitignored — never commit it):

       HUMORHIST_TELEGRAM_BOT_TOKEN=123456:ABC...
       HUMORHIST_TELEGRAM_CHAT_ID=987654321

Only updates from that numeric private chat and matching sender ID are handled.

**Run it**

    python -m humorhist.cli --db data/humorhist.sqlite telegram-review

It long-polls forever — run it as a durable `systemd --user` unit (see
`scripts/telegram_review.py`) so it survives logout:

    systemctl --user status humorhist-telegram.service
    journalctl --user -u humorhist-telegram.service -f

When installed as a `systemd --user` unit with `Restart=always`, the bot can
survive logout when user lingering is enabled. On startup it sends the guided
menu, then **proactively nudges** you with
"🆕 N new draft(s) awaiting review" whenever fresh drafts appear (from `/draft`,
the weekly timer, etc.) — you don't have to remember to poll it.

Drafts and action prompts identify the topic by title and `#short_code`.
For draft-targeted Telegram commands, use the displayed code with `#` (for
example, `/view #ABC123xy`), the bare code, or the full draft ID. A bare exact
full ID takes precedence over a matching short code; use `#` to select the
short code in that case. Unknown or ambiguous identifiers are rejected.
Buttons use the full ID internally. Mutating buttons and editorial prompts
expire when their draft or queue entry changes; reopen the draft or list to
get fresh controls. Changes to other drafts do not expire them. The bot keeps
per-draft version clocks in SQLite, so this protection survives restarts.

`/later` keeps a draft pending but hides it from ready-to-review lists for 30
days. `/listlater` shows deferred drafts and `/reviewnow` brings one or all
forward. The `/status` pending count is a status breakdown and **includes**
deferred drafts, even though the review-ready list and its nudges exclude
future deferrals.

**Guided menu**

Send `/menu` or `/start`, then choose **Review**, **Queue**, or **Find drafts**.
Review lets you select normal (confirmation) or fast (one-tap decisions) mode.
After decisions and completed joke/notes prompts, use the offered review button
to continue. Fast mode is an explicit choice; old normal-mode buttons remain
normal. Skip buttons are available for the joke and optional notes.

Find drafts offers separate Harvest, Screen and Draft buttons. Harvest collects
candidates only; it does not create drafts. Screen and Draft use an LLM and may
incur charges. Their menu buttons are single-use: reopen Find drafts for fresh
buttons, including after a bot restart. Jobs run in the bot process and do not
survive a restart.

Queue rows offer **Export** and **Mark manually posted** together. Export is
read-only and does not post; mark only after posting yourself. The mark requires
confirmation and can be undone from the confirmation response or `/listposted`.
Per-item exports do not disclose local image paths; a long link that cannot fit
intact is supplied in an attached UTF-8 text document.

**Commands**

    /reviewdraft   review pending drafts one by one (✅ Approve / ❌ Reject / ⏸ Later)  (`/reviewdraft fast` commits on the first tap, skipping the confirm gate)
                  a tap opens a Confirm/Cancel gate so a fat-finger can't commit;
                  on Approve confirm, the bot asks for your one-line joke, then notes
    /listlater    list deferred drafts; tap one to bring it forward now
    /reviewnow [<id>]  bring a deferred (/later) draft — or ALL — back for review
    /setjoke <id> set the one-line joke on an approved draft (fixes a blank capture)
    /jokes      list approved drafts missing their one-line joke (tap 📝 to fill one)
    /notes <id>    pending: steer the angles with a note (regenerates on reply);
                   approved: add editor notes (same as the Add notes button)
    /later <id>    defer a pending draft 30 days
    /listapproved  list drafts you've greenlit; tap to open, or ❌ Reject
    /listrejected  list rejected drafts; tap one to reopen for re-review
    /listqueue     list approved+queued drafts; edit, remove, reject, reopen or mark posted
    /listposted    list recorded posts; undo a manual posted record when needed
    /view <id>     open any draft's full content
    /viewcopy <id> open a queued draft's post copy (✏️ Edit / 🔄 Regenerate)
    /queue         list the publish queue (approved+queued drafts)
    /queue enqueue  sweep approved drafts into the queue
    /queue remove <id>  pull a draft back out of the queue (kept approved)
    /harvest       top up the candidate pool from seed + Wikipedia lists
    /screen [limit]  LLM-score unscored pool candidates
    /draft [count] [min_score]  fact-check + generate angles for top candidates
    /suggest <topic>  add an editor-suggested event to the pool
    /buffer        buffer health report + on-demand top-up
    /buffer enqueue  also sweep approved drafts into the queue
    /status        approved / rejected / pending breakdown (+ stuck-capture nudge)
    /publish       read-only export of queued posts (copy + link + image + readiness)
                   for manual pasting — DM'd to your chat; nothing posted automatically
    /menu, /start  open the guided menu
    /help          full command reference

**Examples** (what you type → what happens)

    /harvest
        → reports candidates added, duplicates, invalid rows and Wikipedia
           pages read/failed. Partial source failure is reported as incomplete.
           It collects candidates, not drafts; use /screen and then /draft.

    /screen 50
        → scores up to 50 unscored candidates and reports scored and failed
           counts. Requires an available LLM credential and may incur charges.

    /draft 4 8.0
        → "✍️ Drafting 4 candidate(s) (min score 8.0)…" then "✍️ Drafted 4 new
           draft(s). 9 pending total — send /reviewdraft to review them."
           The reported pending total is the number currently ready for review.
           `/buffer` can also start an on-demand draft top-up.

    /suggest The Great Emu War
        → adds the suggested topic to the candidate pool for a future
           screening and drafting pass.

    /reviewdraft
        → 📊 progress block, then one draft at a time with ✅/❌/⏸ buttons.
        Tapping ✅ (or ❌) opens a **Confirm / Cancel** gate — nothing is
        committed until you tap "Yes, Approve"/"Yes, Reject" (↩️ Cancel backs
        out with no change). After a confirmed Approve the bot asks for your
        one-line joke (the human voice); you send it → "📝 Saved. Optional notes?"
        → /skip. The source link is populated on enqueue. Images are generated
        only when explicitly requested with `/image <draft_id>` — see below.
        On a *pending* draft, tap the **Add notes** button on its content view, then reply
        with your steer (e.g. "lean into the bureaucracy") to regenerate the angles
        with that as steering.

    /later #ABC123xy
        → the named title and code are deferred 30 days (still pending, but
          not shown for review until then).
        List deferred drafts with /listlater; bring one (or all) back with
        /reviewnow [<id>].

    /listlater
        → "⏸ Deferred drafts (tap to bring one forward for review):" with a
           ⏩ Review now button per row; tapping clears the defer and returns
           the draft to the review queue.

    /reviewnow
        → "⏩ Brought forward N deferred draft(s) — they're back in the review
           queue." (or /reviewnow d4f1a2b3 for just one).

    /setjoke d4f1a2b3
        → prompts for the one-line joke on an already-approved draft whose joke
           was never captured (a "stuck capture"), then you reply with it.
           (No status/queue change — just fills the blank human voice.)

    /jokes
        → lists only the drafts still missing their one-line joke, each with the
           topic title + a 📝 Add joke button. Tap one to fill it, or /setjoke <id>.
           (Short for hunting stuck captures without scanning /status.)

    /listapproved
        → list of greenlit drafts, each with a 👁 button to open its content
          and a ❌ Reject button (confirm-gated) to un-approve it on the spot.

    /listqueue
        → "📋 Queued drafts (3) — edit copy before publishing:" with one row
          per draft: ✏️ <title> (open copy), 🗑 Remove (keep approved), ❌ Reject
          (with confirm — fully un-approves), ↩️ Reopen (back to pending),
          📤 Export and ✅ Mark manually posted.

    /viewcopy d4f1a2b3
        → the post copy + N/280 count + ✏️ Edit / 🔄 Regenerate buttons.

    /queue
        → same list as /listqueue (approved+queued drafts).
    /queue enqueue
        → "📥 Enqueued 2 approved draft(s) into the queue." + the queue list.
    /queue remove #ABC123xy
        → removes the named title and code from the queue (kept approved).

    /status
        → approved / rejected / pending breakdown; if any
           approved+queued draft is missing its one-line joke, a ⚠️ stuck-capture
           nudge lists them (or run /jokes for a dedicated list; fix with /setjoke <id>).

    /buffer
        → buffer health (pending/queued counts, level) + on-demand top-up if
           the LLM key is set.
    /buffer enqueue
        → sweep approved→queue first, then the health report.

If an LLM-backed command has no credential, you get a clean
"⚠️ LLM unavailable: …" message instead of a crash (set HUMORHIST_LLM_API_KEY
for unattended use).

**What you do in Telegram**

1. Send **/menu** and choose Review, or send **/reviewdraft** directly. The bot DM's a **📊 Review progress** block
   first: ✅ approved topics, ❌ rejected topics, and ⏳ how many are still
   pending — so you can see at a glance what's already been decided.
2. Then it sends **one draft at a time**. A draft may arrive as a few short
   messages (Telegram caps a message at 4096 chars, so long drafts are split);
   the **✅ Approve** / **❌ Reject** buttons are on the last message of that
   draft. Tap one.
3. In normal mode, tapping a button does **not** commit instantly. It opens a **Confirm /
   Cancel** gate — tap **Yes, Approve** / **Yes, Reject** to commit, or
   **↩️ Cancel** to back out with no change (this stops a fat-finger tap from
   enqueuing a draft before you can reconsider). After a confirmed Approve the
   bot asks for your **one-line joke** (the human voice), then optional notes —
   type the joke and send it, or use the skip button or `/skip` to leave it blank.
   Submitting or skipping triggers a best-effort LLM copy-generation attempt
   if a client is available and may incur charges. (The joke is attached as
   `editor_line` and steers that copy.) On a *pending*
   draft you can also send **/notes <id>** to steer the angles with your note.
4. Tap **Next draft** or send **/reviewdraft** again to advance. You can move
   on without deciding: the previous draft stays pending. Navigation wraps to
   the start of the ready list and excludes future-deferred drafts. If none are
   ready but some are deferred, the bot points you to **/listlater**. New ready
   drafts can also trigger a nudge.

**Browse and annotate approved drafts**

Send **/listapproved** to see every draft you've greenlit. Each row has a
**👁** button to open its full content (rendered just like the review view)
and a **❌ Reject** button (confirm-gated) to un-approve it on the spot — so
a mistaken Approve is reversible from chat without the CLI. Tap **👁** to open
the draft; the content message ends with an **✏️ Add notes** button — tap it to
add more notes later: the bot prompts, you reply (or `/skip`), and the note is
saved on the draft. Re-saving notes is idempotent and keeps the draft in the
publish queue.

Opening an approved draft also shows its **post copy** with a live **N/280**
char count, plus a **📝 Copy** button that jumps straight to the edit/regenerate
view (see below) — so you can read and tweak the caption right from the draft
view without switching to `/listqueue`. If the draft has no copy yet it shows
`0/280` and a hint to generate one.

### 4c. Post copy (generate + edit before posting)

Approving a draft adds it to the queue. In Telegram, submitting or skipping the
joke triggers a best-effort LLM post-copy generation attempt when a client is
available; it may incur charges and can fail or leave copy missing. The prompt
warns before this step. The copy target is `HUMORHIST_CHAR_LIMIT` (default 280).
You can edit or regenerate copy; posting itself remains manual.

**CLI**

    python -m humorhist.cli --db data/humorhist.sqlite copy show <id>     # copy + N/280
    python -m humorhist.cli --db data/humorhist.sqlite copy edit <id>     # $EDITOR, or typed prompt
    python -m humorhist.cli --db data/humorhist.sqlite copy regen <id>    # regenerate via LLM

`edit` opens your `$EDITOR` (falls back to a typed prompt if none is
available); it warns (does not block) if your edit exceeds the active limit.
`regen` overwrites the stored copy with a fresh LLM draft.

**Telegram**

    /listqueue     list queued drafts, each row with ✏️ Edit copy,
                   🗑 Remove (keep approved), ❌ Reject (with confirm),
                   ↩️ Reopen (back to pending)
    /viewcopy <id> open a draft's post copy with inline ✏️ Edit / 🔄 Regenerate

Tap **✏️ Edit** and reply with new copy (or `/cancel` to keep the current);
tap **🔄 Regenerate** to overwrite it with a fresh LLM draft. The stored copy is
updated on `queue.post_copy`. The ❌ Reject and ↩️ Reopen buttons let you
fully un-approve an approved+queued draft or send it back to pending for
re-review — all from chat (see "What you do in Telegram" above).

**Bulk copy regeneration — destructive to existing copy**

    python scripts/fill_approved_copy.py

This script always uses `force=True`: it attempts to regenerate copy for every
approved, unpublished queue row, including rows with existing edits. It uses
`data/humorhist.sqlite` under the repository root rather than the CLI `--db`
option, and uses the unattended credential path. It may incur LLM charges and
overwrite edited copy. Do not run it as a missing-copy-only backfill.

## Editorial note (taste filter)
-------------------------------------------------------------------------------

By deliberate decision, humorhist does NOT down-rank or refuse events involving
death, tragedy, or suffering. The screen prompt scores purely on absurdity, and
the fact-check pass does not emit sensitivity flags. That means grim material
(e.g. famine, fatal accidents) is eligible for drafting alongside the silly
stuff. If you want a different line, edit:

    humorhist/harvest/screen.py   -> SCREEN_SYSTEM_PROMPT
    humorhist/factcheck.py        -> FACTCHECK_SYSTEM_PROMPT

The comic-angle prompt that most affects output quality lives in:

    humorhist/brief.py            -> ANGLES_SYSTEM_PROMPT

## Project status
-------------------------------------------------------------------------------

Built: harvest, screen, draft, CLI and Telegram review, an editable approval
queue, optional image generation, manual-post exports and optional scheduled
discovery and buffer monitoring. Approval enqueues a draft; generated post copy
is best-effort and may be absent. Nothing posts to a social network automatically.

**Story images:** request an image explicitly with CLI `image <draft_id>` or
Telegram `/image <draft_id>`. Approval and enqueue never generate one
automatically. The configured FAL or OpenAI provider writes a PNG to
`data/images/<draft_id>.png` (gitignored) and persists its prompt and path on
the queue row. Enqueue separately populates a **"learn more" link** from the
pool's `source_url`, without calling an image provider. Keep keys out of git.

**Telegram-primary (2026-08-07):** the entire pipeline is now drivable from
Telegram, not just review/edit. From chat you can `/harvest` the pool,
`/screen` candidates, `/draft` new drafts (the previously CLI-only upstream
hole), `/suggest` events, `/buffer [enqueue]` to check health and top up, and
review/approve/edit as before. The bot also proactively nudges on new drafts.

**Duplicate-event prevention:** candidates with matching normalized titles can
be merged across sources; this is not semantic matching and does not catch every
spelling variant. Migration preserves existing drafts when consolidating pool
rows, so a merged pool item may retain more than one pre-existing draft.

**Review hardening (2026-08-13):** the Telegram review surface is now fully
undoable from chat. Approve/Reject taps open a **Confirm/Cancel gate** (GAP 3)
so a fat-finger can't commit before you reconsider. Deferred (`/later`) drafts
get a bring-forward path — `/listlater` lists them with a Review-now button,
`/reviewnow [<id>]` (and a `reviewnow:` callback) clears the defer (GAP 4a).
Approved+queued drafts missing their one-line joke (a \"stuck capture\") are
surfaced as a nudge on `/status` and via the dedicated `/jokes` command, fixable
with `/setjoke <id>` or a tap on the 📝 Add joke button (GAP 4b). And an approved
draft can now be un-approved or sent back to pending entirely from Telegram:
`/listapproved` carries a ❌ Reject button and `/listqueue` rows carry ❌ Reject
(confirm-gated) + ↩️ Reopen buttons. All listing buttons now include the topic
title alongside the #short_code so picks are informed. The CLI equivalents
(`reviewnow`, `setjoke`, `reopen`) were added alongside.

Manual posting (by design — no auto-post):
- `python -m humorhist.cli publish` exports every queued, copy-bearing draft: the post text,
  the `source_link` "learn more" URL, and the
  `image_path` when an image exists. Each row ends with a readiness checklist
  (`copy OK | joke OK | image none (optional)`) so you can see at a glance which
  posts are post-ready and which still need a one-line joke. You paste these into
  Bluesky/Mastodon by hand.
- An auto-publisher was prototyped then deliberately removed — you keep control of
  the posting step. No platform credentials or automatic posting timer are needed.

Until you post manually, "publishing" means: read the approved draft with
`python -m humorhist.cli publish` or `/publish` in Telegram, then copy the text
and image into your client. The bulk `/publish` export includes a recorded local
image path; unlike the newer per-item Export button, it does not hide that path.

## Scheduling (weekly discovery)
-------------------------------------------------------------------------------

When installed and enabled, a `systemd --user` timer runs discovery:

    systemctl --user status humorhist-weekly.timer      # next run time
    systemctl --user start humorhist-weekly.service     # force a run; uses network and may incur LLM charges
    systemctl --user cat humorhist-weekly.timer         # view the schedule

The schedule and unit files are deployment-specific; inspect the installed timer
with `systemctl --user cat humorhist-weekly.timer`. The job
(`scripts/weekly_pipeline.py`) does harvest → screen → draft net-new → best-effort
Telegram nudge. The pipeline avoids duplicate stored candidates and drafts:
harvest upserts by stable page id, screen scores only unscored rows, and the
draft step skips any pool item that already has a draft (so your reviewed/
approved work is never overwritten). LLM calls can fail or incur charges even on
reruns; inspect failed results before retrying. User lingering keeps the user
manager alive after logout when enabled.

The optional `humorhist-buffer.timer` runs `scripts/buffer_health.py`. It checks
queue depth and, when fewer than five drafts are ready for review, can attempt
to draft up to ten more with an available LLM. The job alerts on low buffer or
failure, including drafting failure when the publishing queue is healthy. Its
logs report selected, drafted and failed counts and safe failure-stage summaries.

### Screening retries and charges

Screening records an attempt before sending each batch. A failed or interrupted
attempt remains blocked on later runs, even if no score was saved, because the
provider may have charged for it. Runs stop after a provider failure; reports
show unscored, skipped and blocked counts and sanitized failure categories. Empty,
malformed or partial responses stop the run; valid scores are saved and missing
entries remain blocked. A limited CLI or Telegram run reports its selected
unscored count separately from all blocked rows; `screen_all` exits nonzero if
any blocked rows remain, even when its limit was reached. Screening clients must
provide a single-attempt `complete_json_once` method. To explicitly retry
failed (not interrupted/in-progress) attempts, run `python -m humorhist.cli screen
--retry-failed` with the usual database arguments; this may incur charges.
Interrupted `pending` attempts require operator review and a deliberate database
repair after confirming no screening process is active. Never clear those records
while a request may still be in flight. Existing databases have no historical
attempt records, so requests made before this change cannot be identified.


### Screening reservations and recovery

`humorhist --db PATH screen-status` lists reservation IDs and states without
contacting the provider; Telegram `/screen status` shows counts. Pending means
the result is unknown, not that a request was never sent. Failed includes
timeouts and invalid responses; the provider may still have charged. No
automatic retry occurs. After reviewing the cost and provider history,
`humorhist --db PATH screen --retry-failed` explicitly retries failed rows
(and also processes new eligible rows). It never retries pending rows.

Pending recovery is deliberately offline-only: there is no shared lock that
can exclude old software or all entry points. First stop and disable *all*
screening producers, including Telegram, weekly timers, screen_all, CLI and
legacy scripts on every host using this database; verify all their processes
have exited and cannot restart. Back up the database with SQLite's online
backup API, inspect each ID with screen-status and reconcile the provider's
request/billing history. Only if you accept possible duplicate charges, use
SQLite to delete the specific reviewed reservation with a parameterized
`DELETE FROM screen_attempts WHERE pool_id = ? AND state = 'pending'`, commit,
and check the result before restarting producers. The next normal screening
may submit it again. Do not bulk-delete reservations. Never clear while any
producer might be active. Legacy rescreen_60 is disabled; existing scores
are not cleared and no safe bulk rescreen is currently provided.
